# Neport の目的と設計原則

Neport は、Redmine や GitHub Issues などの既存ツールで仕事を管理する中で感じた、日々の使い勝手の課題を解くための OSS を目指す。複数の案件から次にやる仕事を選ぶ。仕事を分解してチームに委ね、依存関係と進捗を見渡す。作業の切り替えから実績を残し、後で計画と照らし合わせる。こうした一連の仕事を、転記や記録の手間を抑えながら一つの場所で扱えることが、Neport の目指す管理ツールの姿だ。

## 誰の、どんな判断を支えるか

- 複数の案件を抱える人は、期限を見渡し、自分の仕事とチームに任せる仕事の共有範囲を決める。
- メンバーは、自分で仕事を分解し、次に取り組むチケットを選ぶ。
- 案件の責任者は、期限、停滞、レビューが必要な成果を把握する。

## 長く維持する原則

1. **記録の手間を減らす。** 作業を切り替える操作から実績を残す。同じ進捗を複数の画面で入力させず、小さな行為のすべてに起票を求めない。
2. **継続する仕事にプロジェクト、終わりのある成果にチケットを使う。** たとえば「講義A」の下に「中間試験を作成」を置き、作問・校正を子にできる。日常の小仕事も専用案件にまとめられる。
3. **共有する進捗と本人の裁量を両立させる。** チームは同じ工程を見る。何に注目するかは各人が選び、その選択の監督を業務にしない。
4. **安心して委譲できることを優先する。** 所属と権限でデータを分け、重要な判断や訂正は後から追えるようにする。
5. **実際の利用価値を設計の基準にする。** OSS の継続開発を支える明示的な仕様・テスト・運用手順を育てる。現行DBや実装の再設計も選択肢に含め、移行コストと失われる情報を判断材料にする。

機能の実装状況、将来構想、今回扱わない範囲は[要求台帳](REQUIREMENTS.md)に記す。
