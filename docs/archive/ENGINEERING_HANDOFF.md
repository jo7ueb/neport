## 合意した要求と検討中の技術案

**合意済み**　案件は所属者内で共有し、孤立案件を生まない。編集可能な案件ではメンバーが全票を分解・編集でき、責任者が完了・削除をレビューできる。独自ワークフローを残し、標準の Backlog / ToDo / Doing / Done と案件盤面は一つの進捗を使う。個人の注目票は本人が選ぶ。工数は共通画面で切り替え、打刻外の「その他業務」も記録する。停止忘れは本人が直し、締め解除を追跡する。案件間のチケット移動は将来要求。[要求と対象範囲](../REQUIREMENTS.md)・[進捗の判断記録](../adr/0001-ticket-progress.md)

| 問題・リスク | 推奨案と代替 |
|---|---|
| メンバー0人の旧案件は認証済み全員に開く。案件作成と所属登録が別操作で、途中失敗でも同じ状態になり得る。親・マイルストーンの案件一致、依存操作と関連先の認可も不足。 | 先に所属と関連先を保証し、案件と初期責任者を一括確定。既存データは選択移行か新規構築を比較する。越境依存は両端の可視性を設計し、親子とは別に扱う。 |
| チケットは読込時の値を補って全項目を更新し、その後に履歴を書く。同時編集や途中失敗で更新消失・履歴欠落の可能性。 | 更新と履歴を一括確定し、版の比較か行ロックで競合を扱う。レビュー判定も確定時の状態で行う。 |
| 現行画面の案件別全ページ取得と、票ごとの再帰集計を横断画面に流用すると負荷が増える。 | サーバーで可視条件を適用し、カードに必要な列だけをページング。まず閲覧専用の横断盤面を出せる。更新対応では許可遷移先が複数なら具体状態を選ぶ。 |
| 状態履歴から人時を算出すると、放置中や複数人の作業を誤計上する。 | チケット／その他の作業区間を打刻と別に保存し、切替を一括確定。打刻への関連づけは業務規則に必要な場合の選択肢。過去の滞在時間を工数に変換しない。 |

## オーナー判断

[判断台帳 Q1–Q6](../REQUIREMENTS.md)が更新先。次の順で決めると手戻りが少ない。

1. 所属なし案件の引受人・保存対象とサイト管理者の例外。直接移管か受理・後続票方式かは、同一ID、過去工数・添付・履歴をどちらの案件に残すかで選ぶ。
2. 旧状態の標準列への割当、完了・削除の承認必須範囲、個人案件の自己確定、本人が選べる候補の範囲。
3. 打刻外のチケット計時、親への直接計上、「その他」を含む実績の閲覧者、日報承認と月締めが新しい工数のどこまでをロックするか。
