# ADR 0002　仕事管理の正本と外部実行システムの責任分界

**状態**　合意済み（責任分界・運用原則）。2026-11-23。GitHub連携のAPI・データモデル・自動化仕様は未決。

**関連**　[プロダクト方針](../PRODUCT.md)、[要求 R2〜R4・R6](../REQUIREMENTS.md)、[ADR 0001](0001-ticket-progress.md)、[横断盤面・個人の注目リスト仕様案](../specs/boards-and-focus.md)、[現状とのギャップ分析](../WORK_MANAGEMENT_GAP_2026-11-23.md)。

## 背景

研究、授業、校務、開発、運用など、種類の異なる仕事を一元管理したい。一方、研究の仮説・候補実験・実装・考察、あるいはAIエージェントの実行指示には、GitリポジトリやGitHub Issues/PRが向いている。これらをすべてタスクとしてNeportへ転記すると、二重管理が発生する。

Neportの価値を「今日やるべき仕事をNeportだけで把握でき、実行場所には必要なとき移動できること」として検証する。ただし、着想のすべてをNeportに登録することは求めない。

## 検討した選択肢

1. **NeportとGitHub Issuesの双方でタスクを管理する。** 各ツールでは便利だが、期限・優先順位・状態の正本が二つになり、同期と転記が必要になる。
2. **Neportを仕事管理の正本とし、GitHub Issuesを外部実行への依頼・開発上の受け口とする。** プロジェクト横断の計画をNeportへ集約しつつ、実行システムは独立して動かせる。
3. **GitHub Issuesを仕事管理の正本とする。** コード開発には自然だが、授業・校務・研究室運用を横断する管理に適しにくい。

## 決定と理由

**選択肢2を採用する。** 以下は運用上の合意事項であり、すべてが実装済みであることを意味しない。

1. **Neportは仕事の正本。** 研究・教育・校務・開発・運用を横断するプロジェクト、仕事、担当、期限、優先順位、進捗を一元管理する。個人の「今日注力する仕事」をNeportから選べることを目標とする。注目の選択とチームの正式な進捗は別の状態とする（ADR 0001）。
2. **実行すると決めた仕事のみをタスク化する。** 仮説、候補実験、検討中のアイデアを無差別にチケット化しない。必要な作業が明確になった段階でNeportに登録する。研究知識の網羅をNeportに求めない。
3. **分解は必要な場合だけ。** 子チケットは、担当者・期限・進捗を独立して追跡する必要がある場合に作る。単なる手順や微小な作業は説明文、チェック項目、外部成果物などで扱ってよい。これはWBS機能を制限するものではない。
4. **成果・知識の正本は各専門システム。** 研究の仮説・実験計画・コード・結果・考察は対応するリポジトリ、研究室内の手順や共有知識はWiki、その他の成果はその本来の保存先に置く。Neportには管理上必要な要約と参照を置き、内容を複製しない。
5. **GitHub Issueは実行指示であり、Neportのタスクの複製ではない。** AIエージェントに委譲する実装・検証・調査などの実行単位として使う。1つのNeportタスクに複数Issue/PRが対応してよく、失敗や再試行でNeportタスクを増殖させない。GitHubリポジトリのOSS利用者からの不具合報告・改善提案もIssueで受け付けてよいが、それ自体を個人の仕事管理台帳とはしない。
6. **PRは成果のレビュー・承認の場。** IssueのCloseやPRのマージは、Neportタスクの達成を自動的には意味しない。作業依頼の完了と、本来の仕事の達成基準を分離する。
7. **両者は疎結合。** NeportはAI工場がなくても成立し、AI工場はNeportがなくてもGitHubを入口に実行できる。連携は最初から密結合・双方向同期を前提としない。可能な範囲で参照リンクから始め、重複入力を避ける。
8. **単発・突発の仕事も把握する。** プロジェクトに紐づかない小仕事を見落とさない。現行の「小仕事用プロジェクト」を当面利用できる。別のInboxエンティティを作るかは運用検証後に判断する。
9. **権限境界を越えない。** 非公開の研究・業務情報を公開Issueや公開PRへ転記しない。リンク先が閲覧できない場合もNeportで仕事を把握できるようにし、認可・監査を損なう連携を認めない。

## 最小の運用フロー

1. 実際に取り組むと決めた仕事をNeportに登録し、必要なら担当・期限・依存を設定する。
2. Neportの横断候補から今日注力する対象を選ぶ（現状は未実装の部分を含む）。
3. 実行場所を開く。AIへ委譲する場合はGitHub Issueで実行内容と受け入れ条件を指定し、相互参照を残す。
4. GitHub PR等で実行結果を検証する。必要な追試・考察・再依頼は本来のタスクの達成条件に照らして判断する。
5. Neportのタスクを独立して更新・完了する。GitHubでの状態変化による自動完了は設計が確定するまで行わない。

## 影響と未決事項

- Neportの現行チケットは**プロジェクト所属必須**。単発業務はまず専用プロジェクトで扱い、案件非所属タスクやInboxの必要性は実利用で評価する。
- GitHub参照は現行のMarkdown説明欄にURLを記すだけでも開始できる。専用の外部参照モデル、NeportタスクIDのIssue側表現、同期方向、権限と公開範囲は**未決**。
- 横断候補表示・注目リストの実現は既存のR3/R4とIssue #5/#9に沿う。AI連携のためにこれらの優先順位を置き換えない。
- Neport自身の開発用GitHub Issuesは、OSSフィードバック・実装依頼・改修ロードマップの既存の受け口として維持できる。ただし長期的な全体仕事管理をGitHubへ二重化する根拠にはしない。
- 実装順、データ移行、API契約、外部参照の型、イベント連携は本ADRでは決定しない。

## 検証基準

「**今日やるべき仕事をNeportだけで把握でき、実際の仕事をする際にはGitHubやWikiなどへ移動できる。この運用を余計な二重入力なしで成立させられるか**」を、研究・教育・校務・突発業務・AI委譲のシナリオで検証する。
