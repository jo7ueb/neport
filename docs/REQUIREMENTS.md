# プロダクト要求

各行の「要求」は合意した利用者側の期待、「現状」は設計レビュー時点の到達点。根拠と制約は[現行アーキテクチャ](ARCHITECTURE.md)、作業順と進捗は[追跡Issue #2](https://github.com/jo7ueb/neport/issues/2)で管理する。IDは仕様・テストから参照する際に使う。

| ID | 要求 | 現状・残る仕事 |
|---|---|---|
| R1 案件共有 | 個人案件・小仕事用案件を含め、案件はメンバー内で共有し、所属者のいない案件を生まない。 | 部分対応。案件別ロールあり。メンバー0人の旧案件の扱い、作成途中の整合性を改修する。 |
| R2 工程 | 担当を明確にし、深さに仕様上の上限を設けないWBS、先行・後続関係、期限、マイルストーン、ガントで工程を管理する。 | 基本機能は実装済み。越境参照の権限は要整備。将来の案件間移動・受け渡しは別途設計する。 |
| R3 進捗 | Backlog / ToDo / Doing / Done を標準とし、独自状態・遷移を持つ案件でも、横断盤面と案件盤面が同じ進捗を示す。 | 部分対応。現行は案件別盤面。標準4列と現行4カテゴリには意味の差がある。 |
| R4 次の仕事 | ダッシュボードから複数案件の候補を見渡し、本人が注目チケットを選ぶ。期限・担当者・進捗・案件の状態を確認できる。 | 部分対応。自分の進行中と案件別集計あり。未着手を含む横断一覧、選択の保存が必要。 |
| R5 委譲 | 編集可能な案件ではメンバーが全チケットを編集・分解できる。責任者は全体を把握し、完了や削除をレビューできる。 | 部分対応。完了確認と通知あり。削除レビューの段階・対象は未確定。 |
| R6 実績 | 稼働打刻とチケット工数を区別し、ダッシュボードや共通ヘッダーで開始・停止・切替できる。切替で直前の作業を自動停止する。打刻外の「その他業務」もチケットを作らず記録できる。 | 要開発。打刻と日報は実装済み。状態の経過時間から実績人時は分からない。 |
| R7 訂正・閲覧 | 本人が停止忘れを訂正し、実績は権限に応じて閲覧する。締め解除を記録し、解除後に訂正・再締めできる。 | 稼働では本人訂正・監査・月締め解除あり。新しい工数への適用範囲、閲覧者は未決。 |
| R8 品質 | 一覧・詳細・関連データで認可を一貫させ、重要な操作と履歴が一致すること。APIの呼び出し側が成功・拒否・競合を識別でき、再試行や並行操作で記録を失わないこと。 | 基盤あり。API・DBの境界、認可・競合の回帰テストを優先。外部API、UI、バックアップ復元を含む変更影響を検証する。 |

## 時間軸と対象範囲

将来は案件間のチケット移動、見積と実績の比較、案件別・業務分類別の工数分析を行う。優先順位のサジェストとPC操作等からの作業推定は長期構想。初期段階では本人が選ぶ候補と明示操作による計時を優先する。AI開発工場との連携は別プロジェクトで扱う。

## オーナー判断の台帳

推奨案は検討の出発点。採用時に対象仕様と判断記録を更新する。

| ID | 判断点と選択肢 | 推奨案・理由 |
|---|---|---|
| Q1 | メンバーなし案件の引受人、旧データの引継ぎ範囲。再構築か選択移行か。サイト管理者の非所属案件閲覧を通常権限に含めるか。 | 保全対象を棚卸し、未割当は非公開で保留。管理介入と通常の共有範囲を明文化する。 |
| Q2 | 案件間の直接移動（同じID）か、受理時に後続票を作る受け渡しか。越境依存の両端に必要な権限と、非所属側に示す情報は何か。 | 受け渡しなら必要な情報だけを渡せる。直接移動が必須なら、子孫・状態・添付・履歴・過去工数の帰属を先に決める。 |
| Q3 | 既存の未着手を Backlog と ToDo にどう対応づけるか。Done と確認済みを集計上どう区別するか。完了・削除の事前承認は必須か、個人案件で自己確定できるか。 | 案件の具体状態を標準列に割り当て、確認待ちを識別。削除は子孫への影響を確認して確定。個人案件に第二の承認者を求めない案。 |
| Q4 | 個人が選べる候補は担当票だけか、閲覧可能な未担当票等も含むか。 | まず自分の担当を既定表示。選択のために担当・共有期限を変更する手間を避ける。 |
| Q5 | 打刻外のチケット計時、親票への計上を許すか。「その他」を含む個人実績を誰が閲覧できるか。 | 打刻外の「その他」は合意済み。案件にはチケット分だけ集計し、個人全体は本人と指定承認者に限定する案。親子は直接計上と小計を区別する。 |
| Q6 | 月締めと日報承認は新しい工数のどの期間をロックするか。日跨ぎ・月跨ぎの配賦と解除後の再承認はどうするか。 | 対象者のタイムゾーンで期間を決め、締めた実績を変える場合は解除・訂正・再締めを追跡する。 |
