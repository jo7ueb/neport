# 横断カンバンと個人の注目リスト

**仕様案**。対象は[要求 R3・R4、判断点 Q3・Q4](../REQUIREMENTS.md)。[進捗の一元管理](../adr/0001-ticket-progress.md)は合意済み。以下の入出力は論理的な契約案であり、エンドポイントやテーブル名は規定しない。

## 前提・入出力

ログイン中の利用者に、所属とロールの異なる案件がある。既定では活動中の案件を対象とする。候補は本人担当を初期値とする案で、選択可能な最大範囲はQ4で決定する。

| 操作 | 入力 | 結果 |
|---|---|---|
| 候補一覧 | 案件・担当者・期限・標準列の絞り込み、ページ | 読める票のID、件名、案件名、担当者、期限、具体状態と標準列、本人の選択有無。空なら空一覧。件数にも可視条件を適用する。 |
| 選択・解除 | チケットIDと選択後の値。利用者は認証から決める。 | 本人の選択を保存。再送しても重複せず、案件の担当者・期限・状態は維持する。 |
| 遷移 | チケットID、移動先の具体状態、利用者が見ていた状態または版 | 認可・遷移規則を再検証して状態を更新。カード・案件別盤面・詳細を同じ結果で再表示する。 |

## 振る舞いと例外

- **列対応の提案**。具体状態ごとに標準列を割り当てる。たとえば「作問中」「校正中」はともにDoingに置ける。既存の todo だけからBacklogとToDoを自動判別できないため、既存票の割当はQ3で決める。
- 列を移す際、許可された移動先が1件なら使用し、複数あれば具体状態を選ぶ。0件なら更新せず理由を表示する。確認権限、未完了の子孫など、案件側の制限を通す。
- 閲覧者は共有状態を変更できない。個人の選択は本人だけが読み書きする。脱退・削除により読めなくなった票は、保存済みの選択、件数、検索候補からも除く。
- 古い状態を見ていた場合は現在値を再取得し、失敗した移動を画面で確定しない。優先順位の自動提案、案件間移動は対象外。

## 受け入れ例

1. A・Bに所属しCに所属しない利用者が横断一覧を開く。A・Bの条件に合う票だけを取得し、ページを進めても非所属件数を推測できる集計を返さない。
2. Aの票を選んで再ログインすると選択が残る。別ユーザーの注目リスト、Aの担当者・進捗には変化がない。
3. 移動候補が2件あるDoingに移す。具体状態を選ぶまで更新されず、確定後は両盤面と詳細で同じ状態になる。
4. 表示後に閲覧者へ降格、または案件がアーカイブされたとき、旧画面からの移動は拒否される。候補一覧の取得失敗時は空一覧と区別できる。
